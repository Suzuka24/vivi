# plan1：预览缓存、复制图像与菜单显隐

## 计划

### 目标与范围

本记录只确定下一轮要做的改动；本轮不修改功能或设置，不打包或安装插件，仅提交本计划。用户希望尽可能将完整 stack 缓存在本机内存，取消人为的预览尺寸和预加载内存预算限制，并让当前帧就绪后立即开始预加载。

1. 移除 `vivi.maxPreviewSize` 和 `vivi.preloadMaxMiB` 两个设置及其运行时上限；同步检查后端 `render` 的固定尺寸上限、`preloadFrameOrder` 对超过 512 帧的数量限制、缓存淘汰逻辑和按区域读取逻辑。目标是尽可能完整地加载原始分辨率的全部切片；对内存不足给出可恢复的错误，而不是静默截断或使进程崩溃。不要以新的固定预算替换旧预算。
2. 取消 `schedulePreload()` 中的 180 ms 延时。当前帧可显示后立即开始后台预加载，交互请求仍应能优先响应；检查重复调度、取消和重入。
3. 在图像右键菜单和 `Image` 菜单增加“复制图像”。复制结果应与直接截取当前显示的图像区域一致，包括当前 B&C、LUT、视图变换和可见叠加层；不把原始像素简单转成剪贴板文本。实施前确定有选区时复制整幅可见图像还是仅复制选区，以及是否包含十字线等交互标记。
4. 将当前 `vivi.explorerContextMenu` 的自定义字符串列表式配置改为逐项勾选式显隐配置。列出已实现及 TODO 菜单项，层级最多两级，例如 `Image > Type`，默认全部显示。实施时梳理 Explorer 右键、图像右键和顶部菜单栏的菜单数据源，并在设置名称或范围不准确时调整；显隐不应误改命令本身的可用性。
5. 预览跨远程传输应保留源图像的原始数据类型，不再把 `uint8`、`uint16` 或常规 `float64` 无条件转为 `float32`。实施时同时处理字节序、通道、非有限值、FITS `BSCALE/BZERO/BLANK` 对物理值的影响，以及前端的 TypedArray 解码与精确像素值。

### 当前代码依据

- `media/viewer.js` 的 `schedulePreload()` 使用 `setTimeout(preloadFrames, 180)`；`preloadFrames()` 按顺序串行请求，在 `preloadMaxMiB` 预算处停止。
- `media/display.js` 的 `preloadFrameOrder()` 对超过 512 帧的 stack 最多安排 48 帧附近预取。
- `src/extension.js` 将 `maxPreviewSize` 和 `preloadMaxMiB` 传入 viewer，并对 `render` 请求再次限制尺寸；`backend/worker.py` 的 `render()` 还固定夹在 64–2048 像素范围。
- `backend/worker.py` 在 `raw` 预览分支把源数组转为 `float32`，极端值超过其范围时改为 `float64`；`media/viewer.js` 目前只按 `float32` 或 `float64` 解码。这不满足按源 dtype 传输的要求。
- Flip 和 90° rotate 的原始 stack 变换由远端后端执行并写入派生 TIFF；本机仅同步变换已有缓存预览以立即显示。任意角度 rotate 由远端生成派生 TIFF，现有缓存失效后重新读取。

### 验证方式

- 覆盖 `uint8`、`uint16`、有符号整数、`float32`、`float64`、大端 FITS 与多通道图像的往返数值和 dtype；比较当前帧、远距离帧、全 stack 缓存和大于 512 帧的行为。
- 用远程 Cursor 观察首次显示、后台加载、随机跳帧、B&C/变换后缓存复用、内存占用和错误恢复；为服务器读取、编码、SSH/扩展传递与前端解码分别计时。
- 验证剪贴板图像与画面截图逐像素一致，菜单显隐项全部可勾选且默认全选；运行静态检查、测试、打包并审查差异。

## 实施记录

- 2026-09-20：仅记录 plan1。尚未实施上述改动。
- 同日补充传输方案讨论：当前 `raw` 路径通常强制转为 `float32` 并以 Base64 嵌入 JSON；应先让缓存与传输保留源 dtype、shape、字节序和必要的 FITS 标定信息，再选择无损压缩。测试文件 3 张 `float32` 切片每张为 2,528,100 字节；zlib 1 级直接压缩为原体积的 89.5%–91.1%，先进行字节重排后再压缩为 65.9%–79.9%，解压后字节完全一致。该测试只测服务器端压缩率与耗时，尚未测 Cursor 端到端收益。

## 总结

- 本轮没有修改产品行为；这些改动留待后续一起实施。
- 尚未解决的设计细节：有选区时复制的范围、极端大 stack 内存不足时的恢复方式，以及菜单显隐设置的最终命名与各菜单范围。
